## A. 제품 포지션 재정의

리서치 결과를 반영해 한 문장을 이렇게 다듬을 것을 제안합니다.

> **기존 안**: "초보 유튜버가 오늘 무엇을 만들어야 할지 결정하고, 실제 업로드까지 끝내게 해주는 콘텐츠 운영 시스템"

> **제안**: 그대로 갑니다. **다만 홍보의 무게중심을 앞쪽(결정)이 아니라 뒤쪽(끝까지 끝내게)에 둡니다.**

이유: "AI가 추천해준다"는 TubeBuddy가 지난달 출시했고 YouTube가 무료로 합니다(리서치 2-1). 반면 **"업로드까지 끝내게 해준다"는 아무도 안 합니다**(리서치 2-3). 같은 문장이라도 어디에 강세를 두느냐로 제품이 달라집니다.

한 줄 홍보 문구 후보:
- "아이디어는 이미 충분합니다. 문제는 끝까지 못 만드는 것입니다."
- "추천받고 끝나는 도구 말고, 업로드까지 같이 가는 도구"

**핵심 지표는 사장님 안대로 "추천 → 프로젝트 전환율"을 씁니다.** 다만 리서치를 보면 그보다 한 단계 더 중요한 지표가 하나 더 있습니다:

> **프로젝트 → 실제 업로드 완료율**

전환율만 보면 "결정은 잘 시키지만 아무도 안 만드는" 상태를 놓칩니다. Spotter가 죽은 자리가 정확히 거기입니다. **두 지표를 함께 봅니다.**

## B. MVP 범위 — "루프 한 바퀴, 최소한으로"

**목표: 실제 초보 유튜버 5~10명이 이 서비스만으로 영상 1개를 기획→촬영→업로드까지 끝내는 것.**

### MVP에 넣는 것

| # | 기능 | 왜 필요한가 |
|---|---|---|
| 1 | 추천 3개 (순위 + 이유) | 루프의 입구 |
| 2 | **"이 영상으로 결정" → 프로젝트 생성** | 제품의 심장 |
| 3 | 제목 후보 생성 | 결정 직후 바로 쓸모를 느끼는 지점 |
| 4 | 촬영·편집 체크리스트 | 실행 레이어 = 진짜 차별점 |
| 5 | 상태 전환 (기획중→촬영중→편집중→업로드 완료) | 진행 중이라는 감각 |
| 6 | **성과 수동 입력** (조회수 등) | 루프를 닫는 조각 |
| 7 | 홈 화면 "오늘 뭐 할까" | 재방문 이유 |
| 8 | 전환율/완료율 측정 (내부용) | 검증 도구 |

### MVP에서 빼는 것 (그리고 왜)

| 뺄 것 | 이유 |
|---|---|
| **YouTube API 연동 전체** | 파생 지표 정책, 검색 쿼터 100회/일, 7일 토큰 만료, 2~3주 심사, 48시간 지연 — 전부 한꺼번에 옵니다 (리서치 5장). MVP는 성과 **수동 입력**으로 대체 |
| **썸네일 생성** | YouTube Studio가 무료로 합니다. 차별점 아님 |
| **영상 기획서(섹션 구성)** | 위와 동일. 게다가 만들기 무겁습니다 |
| 캘린더 / 일정 관리 | 영상 1개도 못 끝내는 사람에게 캘린더는 이릅니다 |
| 랜딩 페이지 완성 | 첫 사용자 10명은 손으로 모읍니다 |
| 결제 / 요금제 | 검증 후 |
| 채널 전략 화면 | 만들되 **화면에 보여주지 않고** 추천 프롬프트의 내부 입력으로만 씁니다 |

> **가장 크게 줄인 부분이 YouTube API입니다.** 이 하나를 빼는 것만으로 출시가 몇 주 앞당겨지고, 정책 위반 위험이 사라집니다. 루프가 실제로 작동한다는 걸 확인한 다음에 붙여도 전혀 늦지 않습니다.

## C. 새 개발 순서 (STEP 4부터)

각 STEP은 지금까지처럼 **한 번에 하나씩, 검증 후 다음**으로 진행합니다.

### 【1차 — 루프 만들기】

**STEP 4 — DB 최소 확장** (마이그레이션 1개, 반나절)
새 컬럼만 추가합니다. 기존 테이블/정책은 건드리지 않습니다.

**STEP 5 — AI 추천 3개** (첫 AI 기능)
Vercel AI SDK `generateObject` + Zod로 구조화된 출력. `/recommend` 화면. `ai_generations`에 기록.

**STEP 6 — "이 영상으로 결정" → 프로젝트 생성** ★가장 중요
`content_projects` 생성 + `idea_id` 연결. 중복 방지는 **이미 있는 partial unique index가 그대로 해줍니다** (새로 만들 것 없음).

**STEP 7 — 프로젝트 상세 + 제목 후보 생성**
제목만. 썸네일·기획은 안 만듭니다.

**STEP 8 — 촬영·편집 체크리스트**
(→ 확인 필요 1번: AI 생성 vs 고정 템플릿)

**STEP 9 — 상태 전환 + 업로드 완료 + 성과 입력**
"업로드 완료" 누르면 성과 입력을 유도.

**STEP 10 — 홈 화면 "오늘 뭐 할까"**
진행 중 프로젝트가 있으면 그걸, 없으면 추천을 보여줍니다. (지금의 임시 대시보드를 여기서 교체)

**STEP 11 — 전환율/완료율 측정**
별도 분석 도구 없이 SQL + 간단한 화면.

### 【2차 — 실제 사용자 테스트】

**STEP 12 — 초보 유튜버 5~10명 테스트**
코드보다 이게 더 중요합니다. 여기서 나온 결과로 3차를 정합니다.

### 【3차 — 검증 후에만】

STEP 13+ : YouTube API 연동 / 썸네일 / 영상 기획서 / 캘린더 / 랜딩 / 요금제
**루프가 작동한다는 증거가 나오기 전에는 손대지 않습니다.**

## D. DB 변경 계획 (STEP 4 상세)

### D-1. 새 마이그레이션 파일 1개: `0005_pivot_columns.sql`

**`video_ideas` 테이블에 컬럼 3개 추가**

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `rank` | `smallint` (null 허용) | 추천 순위 1~3위. 추천이 아닌 아이디어는 null |
| `batch_id` | `uuid` (null 허용) | 한 번의 추천으로 나온 3개를 묶는 식별자. **전환율 계산의 핵심** |
| `dismissed_at` | `timestamptz` (null 허용) | "이건 별로예요" 누른 시각 |

**`content_projects` 테이블에 컬럼 3개 추가**

| 컬럼 | 타입 | 용도 |
|---|---|---|
| `result_views` | `integer` (null 허용) | 사용자가 직접 입력한 조회수 |
| `result_recorded_at` | `timestamptz` (null 허용) | 성과를 기록한 시각 |
| `result_note` | `text` (null 허용) | "생각보다 반응이 좋았다" 같은 메모 |

**인덱스 1개 추가**
```
video_ideas (user_id, batch_id)
```

### D-2. RLS / GRANT는 건드리지 않습니다 ✅

중요한 안심 포인트입니다. **PostgreSQL의 RLS 정책과 GRANT는 테이블 단위로 걸려 있습니다.** 컬럼을 추가해도 기존 정책(`auth.uid() = user_id`)과 권한이 **자동으로 새 컬럼에도 적용**됩니다. 0002/0004 파일을 다시 실행할 필요도, 수정할 필요도 없습니다.

### D-3. 왜 새 테이블을 안 만드는가

- **추천 묶음(batch)**: 별도 테이블 대신 `batch_id` 컬럼 하나로 충분합니다. `group by batch_id`로 다 계산됩니다.
- **성과 데이터**: 지금은 "영상 1개 = 프로젝트 1행"이고, 기록도 한 번만 하면 됩니다. 나중에 "7일차/30일차 성과"처럼 시간에 따라 여러 번 기록해야 할 때 별도 테이블로 옮기면 됩니다. **지금 만들면 안 쓰는 테이블이 됩니다.**

### D-4. 타입 재생성
```powershell
npm.cmd run types
```
이미 `package.json`에 있는 스크립트입니다. 그 뒤 `lib/types.ts`에 새 컬럼용 타입 몇 줄만 추가합니다.

### D-5. 위험도: 낮음
- 전부 **nullable 컬럼 추가**라 기존 데이터가 깨지지 않습니다
- 기존 코드는 새 컬럼을 모르므로 그대로 동작합니다
- 되돌리기도 쉽습니다 (`alter table ... drop column`)

## E. 추천 → 프로젝트 전환율 측정 방법

**별도 분석 서비스(Amplitude, Mixpanel 등)를 붙이지 않습니다.** 이미 있는 테이블로 계산됩니다.

```sql
-- 추천 묶음(batch) 단위 전환율
-- "3개 추천했을 때 그중 하나라도 프로젝트가 된 비율"
with batches as (
  select distinct user_id, batch_id
  from public.video_ideas
  where batch_id is not null
),
converted as (
  select distinct i.batch_id
  from public.video_ideas i
  join public.content_projects p on p.idea_id = i.id
  where i.batch_id is not null
)
select
  count(*)                                          as 추천_묶음_수,
  count(c.batch_id)                                 as 전환된_묶음_수,
  round(100.0 * count(c.batch_id) / nullif(count(*),0), 1) as 전환율_퍼센트
from batches b
left join converted c on c.batch_id = b.batch_id;
```

```sql
-- 프로젝트 → 실제 업로드 완료율 (더 중요한 지표)
select
  count(*)                                                     as 만든_프로젝트,
  count(*) filter (where status = 'PUBLISHED')                 as 업로드_완료,
  round(100.0 * count(*) filter (where status = 'PUBLISHED')
        / nullif(count(*),0), 1)                               as 완료율_퍼센트
from public.content_projects;
```

추가로 **순위별 선택률**(1위를 고르는가, 3위를 고르는가)도 `video_ideas.rank`로 바로 나옵니다. 이게 추천 품질을 판단하는 좋은 신호입니다.

## F. AI 설계 (STEP 5 상세)

- **기술**: Vercel AI SDK의 `generateObject()` + Zod 스키마 → 형식이 어긋난 AI 응답이 DB에 들어갈 수 없습니다
- **호출 위치**: Server Action 또는 Route Handler (기존 패턴 유지)
- **검증 스키마 위치**: `lib/validations/recommendation.ts` (온보딩과 같은 컨벤션)
- **기록**: `ai_generations`에 `kind='ideas'`, 성공 여부, 토큰 수 (**사용량 제한 코드는 넣지 않음** — 기존 결정 유지)
- **출력 형태**:
  ```
  { rank: 1|2|3, title, category, reason, difficulty }  × 3개
  ```
- **입력**: 온보딩 5문항 + (2회차부터) 지난 영상 성과 요약 + 거절한 주제 목록

**비용 통제**: 앱 코드가 아니라 **AI 제공자 대시보드의 지출 상한**으로 막습니다(기존 결정 유지). 구조적으로 "추천 1회 = LLM 호출 1회"라 비용이 폭발할 수 없습니다.

## G. 보안 / 위험 검토

| 항목 | 판정 |
|---|---|
| **인증** | 변경 없음. 모든 쓰기는 Server Action에서 `getClaims()` 재확인 (기존 패턴) |
| **RLS** | 변경 없음. 컬럼 추가는 기존 정책이 자동 적용 |
| **중복 제출** | 프로젝트 생성 중복은 **이미 있는 partial unique index**가 DB 레벨에서 막습니다. 추가 작업 없음 |
| **AI 응답 신뢰** | Zod로 검증 후에만 DB 저장. 검증 실패 시 저장하지 않고 재시도 유도 |
| **AI 비용** | 제공자 지출 상한. 앱 내 제한 코드 없음 |
| **YouTube API 정책** | **MVP에서 API를 안 쓰므로 해당 없음.** 나중에 붙일 때 "자체 계산 수치"에 고지 문구 필수 |
| **개인정보** | MVP는 성과 수동 입력이라 YouTube 계정 데이터를 저장하지 않습니다. 개인정보 부담이 크게 줄어듭니다 |
| **사업 위험** | 🔴 가장 큰 위험. Spotter 철수 + 0~1만 세그먼트 낮은 지불 의사 (리서치 3장). **STEP 12 사용자 테스트에서 "돈 낼 의향"을 함께 물어봐야 합니다** |

## I. 확인 필요 — 승인해주셔야 진행합니다

### 1. 🔴 추천 재생성을 몇 번까지 허용할까요? (제품 정체성 문제)

"50개 말고 3개"가 핵심인데, **재생성 버튼을 무제한으로 두면 사용자가 마음에 들 때까지 돌려서 결국 50개를 보게 됩니다.** 그러면 차별점이 사라집니다.

- (a) 하루 1회만 — 가장 강한 "결정 강제". 대신 첫인상이 나쁠 위험
- (b) 하루 3회 — 절충
- (c) 무제한 — 사용자는 편하지만 컨셉이 희석됨

*의견: (b)를 권합니다. 단 이건 코드 제한이 아니라 제품 규칙이므로, 이전에 결정하신 "AI 사용량 제한 코드 금지"와는 별개 사안입니다 — 비용 통제가 아니라 UX 설계입니다.*

### 2. 체크리스트를 AI로 생성할까요, 고정 템플릿으로 시작할까요?

- (a) 고정 템플릿 + 사용자가 추가/삭제 — 빠르고, 초보에겐 표준 체크리스트가 오히려 유용. AI 호출 절약
- (b) AI가 영상별 맞춤 생성 — 더 그럴듯하지만 개발·비용 증가

*의견: (a)로 시작을 권합니다.*

### 3. AI 제공자를 무엇으로 할까요?

OpenAI / Anthropic / Google 중 선택이 필요합니다. **STEP 5 시작 전에 API 키 발급이 필요**하고, 발급 절차를 제가 화면별로 안내해드리겠습니다. (키 값 자체는 절대 채팅에 붙여넣지 마시고 `.env.local`에만 넣으시면 됩니다)

### 4. MVP 성과 입력 항목은 어디까지?

- (a) 조회수 1개만 — 입력 부담 최소
- (b) 조회수 + 좋아요 + 댓글 수
- (c) 위 + 구독자 증가 수

*의견: (a)로 시작하고, 사용자가 더 넣고 싶어하면 늘리는 것을 권합니다.*

### 5. 포지션 문구를 "결정"에서 "완주"로 옮기는 것에 동의하십니까?

제품 기능은 그대로지만 홍보·화면 문구의 강세가 달라집니다 (A장 참고).
