# STEP 4-0 중간 결과 — story_01 (실사용자 영상 1개)

영상: `story_01_720p_30fps.mp4` (본인 제작, 720x1280 세로, 30fps, 44.23초, 오디오 AAC)

**이 문서는 STEP 4-0의 최종 결과가 아니라 첫 실제 샘플 1개에 대한 중간 점검입니다.** 정식 사람 라벨링(ground truth)이 아직 없는 항목은 "Claude 예비 확인"으로 별도 표시했고, 점수(P/R/F1)는 계산하지 않았습니다 — 사람이 직접 라벨링한다는 원칙을 지키기 위해서입니다. 영상에 존재하지 않거나 판단할 신호 자체가 없는 항목은 `not tested`로 표시했습니다.

> **추가 참고(2026-08-23, game_01 결과 반영)**: game_01에서 저모션 탐지 방식(화면 전체 평균 YDIF)의 결함이 발견되어 tile/optical-flow/SSIM 대안 신호를 비교했습니다. 이 story_01에도 같은 스크립트(`analyze_motion_candidates.py`)를 돌려 교차 확인한 결과, 이미 아래 1절에서 찾은 컷 후보(2.53s, 11.97s)가 새 대안 신호들에서도 모두 98퍼센타일 이상으로 일관되게 잡혀 — **단일 샷 위주인 이 영상에서는 대안 신호를 도입해도 기존 결과가 달라지지 않는다는 것을 확인했습니다.** 저모션 구간 자체에 대한 threshold는 game_01과 마찬가지로 아직 정하지 않았습니다(사람 ground truth 필요). 상세 수치는 `results-step-4-0-interim-game01.md` 3-1절 참고.

## 1. Scene-change / 시각적 변화 후보 (scdet, threshold=25 — 아래 근거로 선택)

이 영상의 실제 MAFD(프레임간 변화량) 분포를 보면 13~22.5 사이에 완만한 값들이 몰려 있고, 25 이상에서 4개 값(32.4 / 46.3 / 57.0 / 65.9)이 뚜렷하게 튀는 구조였습니다. **threshold=25는 이 분포에서 관찰된 자연스러운 간격(gap)을 근거로 잡은 것이고, 좋은 결과가 나오도록 맞춘 값이 아닙니다** — 영상 1개짜리 분포이므로 앞으로 더 많은 샘플이 쌓이면 이 값 자체도 다시 검토해야 합니다.

| 시각(초) | MAFD | Claude 예비 시각 확인 (사람 검수 필요) |
|---|---|---|
| 2.53 | 56.99 | **실제 컷으로 보임** — 폰 화면 UI에서 완전히 다른 장면(코드 에디터 화면)으로 전환 |
| 11.97 | 65.94 | **실제 컷으로 보임** — 유튜브 앱 화면에서 손으로 물건을 든 장면으로 전환. 블랙프레임 이벤트(11.97–12.1s)와 겹침 — 컷에 짧은 암전 효과를 섞는 편집 스타일로 추정 |
| 21.30 | 46.34 | **판단 애매** — 흰색 플래시/그래픽 효과와 겹쳐 있어 "컷"인지 "플래시 연출"인지 프레임만으로 확실치 않음 |
| 24.37 | 32.40 | **판단 애매** — 마찬가지로 플래시 그래픽 직후 장면이 바뀌는데, 플래시 자체가 컷의 일부인지 별개 연출인지 불확실 |

threshold를 13까지 낮추면 22개 후보가 나옵니다(카메라 움직임/장면 내부 변화가 다수 섞여 있을 것으로 추정) — 참고용으로만 `results/story_01_cuts_candidates_low.csv`에 남겨뒀습니다.

**중요 발견**: 5.23–6.03초 구간(blackdetect가 잡은 페이드 전환)은 실제로는 장면이 바뀌는 지점인데도 MAFD 스파이크로는 거의 안 잡혔습니다(페이드는 서서히 어두워지므로 프레임간 급격한 차이가 안 생김). 즉 **페이드형 전환은 scdet이 아니라 blackdetect 쪽에서 잡힌다**는 걸 실제 영상에서 확인했습니다 — 두 신호를 같이 봐야 하는 이유가 실제 데이터로 확인된 셈입니다.

## 2. 컷 아닌 플래시/급변

이 영상 자체에서 명확히 "컷은 아니지만 플래시만 발생"이라고 단정할 수 있는 구간을 찾지 못했습니다 — 오히려 위 21.30초/24.37초처럼 "플래시 연출과 컷이 겹쳐 있어 구분이 애매한" 사례가 나왔습니다. 이건 사용자가 만들 보조 클립(의도적으로 컷 없는 플래시만 넣은)이 왜 필요한지를 보여주는 사례이기도 합니다. → **부분적으로만 관찰됨, 명확한 사례는 not tested**

## 3. 자막

영상 전반에 걸�쳐 흰색 텍스트 자막이 보였습니다(하단 근처, 반투명 박스 배경으로 추정 — 일반 자막 스타일에 가까움). **OCR 정확도는 이번에 측정하지 않았습니다** — Claude가 프레임을 보고 판독하는 건 측정으로 인정하지 않기로 한 원칙에 따라, `OCR-EXTERNAL-EXECUTION-PLAN.md`대로 실제 OCR 엔진 실행을 기다립니다. 컬러/테두리·그림자/큰 강조/중앙·상단/예능식 짧은 자막처럼 뚜렷이 구분되는 스타일은 이번 영상에서 관찰되지 않았습니다. → **컬러/테두리그림자/큰강조/중앙상단/예능짧은 자막: not tested**, 일반 자막 존재 여부만 육안으로 확인(정확도 미측정)

## 4. Freeze (실제 정지 화면)

`freezedetect` 이벤트가 하나도 감지되지 않았고, 육안으로도 완전히 멈춘 화면은 못 찾았습니다. → **not tested** (이 영상엔 해당 구간이 없는 것으로 보임 — 보조 클립에서 확인 예정)

## 5. 블랙프레임

3건 감지: 5.23–6.03s(0.8초), 10.03–10.27s(0.23초), 11.97–12.1s(0.13초). 육안 확인 결과 셋 다 실제 화면 전환 효과로 보였습니다(1번은 페이드, 3번은 컷+암전 조합). → **탐지됨, 실제로 보이는 것과 일치**

## 6. 음량 급증 / 음량 과소

**측정 불가 — 이유가 다릅니다.** `volumedetect` 결과 mean_volume/max_volume이 **-91dB**로 나왔습니다. 이건 "조용한 구간이 있다"가 아니라 **오디오 트랙 전체가 사실상 무음(음소거 수준)** 이라는 뜻입니다. silencedetect도 0초~44.23초 전체를 무음으로 잡았습니다. → **not tested** — 다만 "이 영상엔 해당 없음"이 아니라 "오디오 신호 자체가 없어서 판단 불가"입니다. **이 영상이 원래 음소거로 편집된 게 맞는지, 아니면 내레이션이 빠진 상태로 잘못 올라간 건지 확인 부탁드립니다** — 다음 실제 영상 샘플에는 정상적인 오디오가 있어야 음량 관련 항목을 실제로 검증할 수 있습니다.

## 7. 자막 없는 발화

오디오가 사실상 무음이라 "발화 구간"이라는 개념 자체를 이 영상에서는 판단할 수 없었습니다. → **not tested**

## 8. 화면 변화가 적은 구간 (정적)

38.17–44.2초 구간이 탐지됐습니다. 육안 확인 결과 브랜드 아웃트로 애니메이션(어두운 배경 + "021 ZERO TO ONE" 로고, 느리게 나타남)으로, 실제로 변화가 적은 구간이 맞았습니다. → **탐지됨, 실제로 보이는 것과 일치**
