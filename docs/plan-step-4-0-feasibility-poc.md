# docs/plan-step-4-0-feasibility-poc.md

STEP 4-0의 research + plan입니다. **이 문서 자체는 계획이며, PoC 실행 코드/production 코드/DB migration/의존성 설치는 아직 하지 않았습니다.** 아래 계획을 승인받은 뒤 실제 PoC를 실행합니다.

---

## 0. 이 STEP의 목적과 범위

STEP 4-0의 목적은 "만들 수 있는가"가 아니라 "실사용 수준으로 정확하고, 감당할 수 있는 시간/비용으로 처리되는가"를 실측하는 것입니다. 범위는 로컬/임시 스크립트로 각 기술을 실제 테스트 영상에 돌려 사람이 만든 정답과 비교하는 것까지이며, Next.js 앱 코드, DB 스키마, 클라우드 인프라(Cloud Tasks/Cloud Run/Supabase Storage 정책)는 이 STEP에서 만들지 않습니다.

## 0-1. PoC 실행 중 발견에 따른 방법론 수정 이력

실제 데이터(game_01)를 테스트한 결과에 따라 사전 계획을 아래와 같이 수정합니다. **임의로 임계값을 조정해 결과를 좋게 만든 것이 아니라, 실측 결과가 사전 설계와 맞지 않아 설계 자체를 바꾼 것**이며, 어떤 데이터를 보고 왜 바꿨는지 아래에 근거를 남깁니다.

- **2026-08-23, 3-3 항목(cut vs scene-change) 정정**: game_01 실측에서 "컷"과 "컷 아님(플래시 등)"의 이분법으로는 설명되지 않는 제3의 유형(메인 레이아웃은 유지된 채 PIP/인서트 영상만 편집으로 교체되는 경우)이 발견되어, 게임 장르에 한해 ground truth를 `full_cut`/`partial_edit`/`game_visual_change` 3분류로 확장합니다. 이에 따라 3-3의 채택 기준 표현도 검증이 충분해지기 전까지는 "컷 수"로 단정하지 않고 `visual change frequency`(화면 전환 빈도) 계열 표현을 유지합니다.
- **2026-08-23, 3-4 항목(low-motion/static) 정정**: 사전 계획대로 `signalstats`의 화면 전체 평균 YDIF로 만든 detect_low_motion.py를 game_01에 돌린 결과 영상의 93% 이상을 저모션으로 오판했습니다(명백한 오탐 — 이 영상은 스트리머가 계속 말하고 반응하는 콘텐츠). **오탐을 숨기려고 threshold를 조정하지 않았고**, 대신 지역별(tile) 신호, 상위 tile percentile/top-k 신호, optical flow, SSIM을 후보로 추가 비교하는 작업을 STEP 4-0 범위 안에서 진행합니다(사람이 라벨링한 static ground truth가 없는 상태에서는 이 후보들 중 어느 것도 최종 채택 threshold를 정하지 않습니다 — 상세는 `results-step-4-0-interim-game01.md` 참고).
- **2026-08-23, 3-1 항목 인접 정정(오디오)**: 음량 급증/과소를 "문제"로 단정하지 않고, `candidate_loud_event`/`candidate_silence`로만 표시하도록 변경합니다. 실제 소리 내용은 Claude가 들을 수 없으므로 사용자가 직접 청취해 ground truth를 추가하기 전까지는 통계적 후보일 뿐입니다.
- **2026-08-23, 제품 표현 정정("low motion" → "low visual change")**: 배치 16 결과(sample_12, 그린스크린 강의)에서 "화면상 시각적 변화가 적음"과 "콘텐츠가 지루함"이 다른 개념이라는 게 확인됐습니다. 지금까지 결과상 low motion = boring이라고 해석하지 않으며, V1 사용자 표현은 `low visual change` / `시각적 변화가 적은 구간`으로만 씁니다. 최종 사용자 피드백은 항상 "관찰 → 근거 → 장르 맥락" 구조를 유지합니다(예: "12.4~18.1초 동안 화면 변화량이 낮았습니다. 다만 강의/토킹헤드 장르에서는 정상적인 구성일 수 있습니다."). 이 표현 원칙은 `plan-v1-revised.md`의 3층 표시 형식과 동일합니다.
- **2026-08-23, scene/visual-change 분류를 6종으로 확장 + 장르 공통화**: 원래 `full_cut`/`partial_edit`/`game_visual_change` 3분류는 게임 장르 전용으로 도입했으나, 배치 16에서 인터뷰 장르(sample_05)에도 자막/오버레이 그래픽 등장이 컷으로 오탐되는 별개 패턴이 확인되어 `transition`(암전/디졸브 등 의도된 전환)과 `overlay_change`(자막/이름표 등 텍스트 그래픽 등장), 그리고 게임 외 오버레이 이펙트를 포괄하도록 `visual_effect_non_cut`을 추가해 총 6분류로 확장하고, 게임 장르 전용이 아니라 **장르 공통 분류**로 전환합니다: `full_cut`, `partial_edit`, `game_visual_change`, `transition`, `visual_effect_non_cut`, `overlay_change`. 앞의 3개(full_cut/partial_edit/transition)는 "실제 편집"으로, 뒤의 3개(game_visual_change/visual_effect_non_cut/overlay_change)는 "편집 아님(오탐 후보)"으로 묶어 precision/recall 계산의 분모/분자로 씁니다.
- **2026-08-23, visual-change recall 측정 방식 보완**: 탐지 후보 목록만 사람이 채점하면 recall(재현율)은 절대 측정할 수 없다는 지적에 따라(후보 목록 자체가 detector가 놓친 걸 담을 수 없으므로), ground truth CSV에 `source` 필드(`detected_candidate`/`human_added_missed_edit`)를 추가했습니다. 사람이 영상을 처음부터 끝까지 후보 목록과 무관하게 독립적으로 다시 보고, 목록에 없는 실제 편집을 발견하면 개수 제한 없이 `human_added_missed_edit` 행으로 추가합니다. `CONFIRM_NO_ADDITIONAL_MISSED_CUTS` sentinel은 "독립 검수했지만 추가로 놓친 게 없었다"는 것을 확인하는 용도로만 남기고, recall 분모는 `(탐지 후보 중 실제 편집) + (사람이 독립 검수로 추가한 놓친 실제 편집)`으로 계산합니다(`score_visual_change_categories.py`).
- **2026-08-23, 검증 범위를 4개 샘플로 한정(확대 아닌 수렴 단계)**: 배치 16 탐색은 여기서 더 넓히지 않고, 지금까지 확보한 데이터로 기술별 채택/조건부/제외 판정을 내리는 단계로 전환합니다. 사람이 확인할 ground truth 대상은 `sample_05`(자막/오버레이발 오탐 검증), `sample_02`(game_01 calibration threshold를 그대로 적용하는 저모션 신호 검증 — 이미 배치 탐색에서 한 번 훑어본 영상이므로 엄밀한 blind holdout이 아니라 "검증(validation) 실행"으로 표현), `sample_14`(게임 이펙트 vs 실제 편집 경계), `sample_06`(컷 탐지 positive-control, precision/recall/F1 확인) 4개로 한정합니다.
- **2026-08-23, 3-4 항목 추가 정정(calibration/holdout 분리)**: 같은 ground truth 데이터에서 threshold를 스캔해 최고 F1을 고르고, 그 F1을 그대로 채택 판정에 쓰면 과적합 위험이 있다는 지적에 따라 평가를 2단계로 나눕니다. **game_01은 calibration/dev 데이터**로만 사용해 5개 신호(whole_frame_diff/tile_max_diff/tile_topk_mean/optical_flow_mag/ssim_change) 각각의 threshold 후보를 탐색하되, 여기서 나온 F1은 최종 성능으로 인정하지 않습니다. **별도의 게임 영상(game_02, holdout)**에서 game_01 calibration으로 고정된 threshold를 그대로 적용해 holdout F1을 구하고, 이 값을 채택(≥0.7)/조건부(0.5~0.7)/제외(<0.5) 판정의 근거로 씁니다. holdout 결과를 본 뒤 threshold를 다시 조정하면 그 결과는 최종 테스트 점수로 인정하지 않습니다. `scripts/evaluate_motion_candidates.py`가 이 calibrate/holdout 흐름을 강제합니다(holdout 서브커맨드는 threshold를 다시 고르는 기능 자체가 없음).

## 1. 인프라 설계 정정 (문서화만, 이번 STEP에서 구현 안 함)

이전 계획 문서의 표현을 다음과 같이 정정합니다. 실제 구현은 STEP 4-3(Job 뼈대) 이후입니다.

### 1-1. Cloud Tasks는 Cloud Run Job을 "직접 오래 기다리며" 호출할 수 없음

- Cloud Tasks HTTP target의 `dispatch_deadline`은 **최소 15초, 최대 30분, 기본값 10분**으로 공식 문서에 정해져 있다.
- 이 시간 안에 대상이 응답하지 않으면 Cloud Tasks는 `DEADLINE_EXCEEDED`로 판단하고 **큐의 재시도 정책에 따라 같은 작업을 다시 큐잉한다.** 즉 FFmpeg+STT 파이프라인이 30분을 넘기거나, 응답을 기다리는 동안 dispatch_deadline을 넘기면 같은 영상 처리가 중복으로 재시작될 위험이 있다 — Google 공식 문서도 "Cloud Tasks의 최대 타임아웃보다 오래 걸리는 작업은 Cloud Run Job을 쓰라"고 명시한다.
- Cloud Run Admin API의 `jobs.run`(`projects.locations.jobs.run`)은 **비동기**다 — 호출하면 Execution을 시작만 하고 즉시 반환하며(Long-Running Operation), 실제 실행은 별도로 진행된다. `gcloud run jobs execute`도 기본값이 non-blocking이고 `--wait`를 줘야 완료를 기다린다.

**정정된 구조 (STEP 4-3 이후 구현 후보, 이번 STEP에서는 미구현)**:
```
Cloud Tasks (HTTP target, 짧은 dispatch_deadline 안에 응답 가능한 대상)
  → lightweight launcher Cloud Run Service
      (역할: jobs.run 호출 후 Operation을 받는 즉시 200/202 반환 — 자기 자신은 처리 안 함)
  → Cloud Run Job 실행 (독립적으로 진행, 완료 여부는 DB 기록으로 스스로 보고)
```
대안으로 Eventarc가 Cloud Storage 업로드 이벤트에서 바로 Job을 트리거하는 패턴도 있으나, 이 경우도 "트리거하는 쪽이 Job 완료를 기다리지 않는다"는 근본 구조는 동일하다. 두 패턴 중 무엇을 쓸지는 STEP 4-3에서 결정한다.

### 1-2. 파일 삭제는 `storage.objects` 직접 DELETE 금지

- Supabase 공식 문서: `storage.objects`는 메타데이터 테이블일 뿐이며, "메타데이터를 지운다고 실제 저장소의 오브젝트가 지워지지 않는다 — 오브젝트는 접근 불가능해지지만 비용은 계속 청구된다"고 명시. 공식 가이드는 "삭제는 반드시 Storage API를 통해서 해야 하며 SQL 쿼리로 하면 안 된다"고 못 박는다.
- 올바른 방법: `supabase.storage.from(bucket).remove([path1, path2, ...])`(호출당 최대 1000개) 또는 동일한 역할의 REST 엔드포인트(`DELETE /object/{bucket}/{path}`). 서버 측에서는 `service_role` 키로 호출.
- 권장 구조: **pg_cron은 스케줄러 역할만** — 정해진 시간에 pg_net으로 Edge Function(또는 Storage API를 호출하는 별도 함수)을 호출하고, 실제 삭제(`remove()`)는 그 Edge Function 안에서 수행한다. pg_cron이 `storage.objects`를 직접 만지지 않는다.

**정정된 구조 (문서화만)**:
```
pg_cron (스케줄: 예 - 매일 새벽)
  → pg_net으로 cleanup Edge Function 호출
      Edge Function 내부:
        - "삭제 대상" 조건에 맞는 video_analyses 행 조회 (예: completed 후 N일 경과)
        - supabase.storage.from(bucket).remove([...]) 호출 (service_role)
        - 삭제 성공 시 DB에도 반영 (예: storage_path를 null 처리하거나 별도 삭제 플래그)
```
이것도 STEP 4-0에서는 구현하지 않고, 정확한 보관 기간(N일)은 개인정보 처리방침과 함께 별도 결정합니다.

## 2. 벤치마크 설계 공통 원칙

- 모든 항목은 **사람이 직접 만든 ground truth**와 자동 예측을 비교하는 방식으로 평가한다. "그럴듯해 보인다" 수준의 육안 확인은 통과 근거로 인정하지 않는다.
- 모든 지표는 **채택 / 조건부 채택 / 제외** 3단계 판정과 함께 기록한다. 조건부 채택은 "이 범위/표현으로만 쓴다"는 구체적 제약을 동반해야 한다.
- 아래 제시하는 구체적 수치 임계값(예: CER ≤15%)은 **사전 가설**이다. 실측 데이터를 보고 나서 조정 가능하며, 이 문서의 목적은 "기준 없이 감으로 판단하지 않는 것"이지 지금 이 숫자를 절대 기준으로 못 박는 것이 아니다.
- 장르(게임/스토리·썰/정보형)별로 결과가 다를 수 있는 항목(특히 컷 감지)은 반드시 장르별로 분리 채점한다.

## 3. 항목별 벤치마크 설계

### 3-1. 한국어 STT 정확도 + timestamp 오차

- **Ground truth 제작**: 테스트 영상별로 사람이 직접 들으며 (a) 정확한 발화 텍스트 전사, (b) 각 발화(문장/구 단위) 시작-종료 타임스탬프를 기록한다. 영상 전체를 다 전사하기보다, 영상당 무작위/계층 샘플링으로 최소 30~50개 발화 구간을 뽑아 정밀 라벨링한다(전체 전사는 비용이 커서 PoC 단계에는 과함).
- **지표**:
  - CER(Character Error Rate, 음절 단위) — 한국어는 교착어라 어절 단위 WER보다 CER이 실질 품질을 더 잘 보여줄 가능성이 높다는 가설로 기본 지표로 삼되, WER도 참고용으로 같이 기록해 실측으로 비교한다.
  - Timestamp MAE(평균 절대 오차, 초) — 예측 발화 시작/종료 vs 정답
- **판정 기준(가설)**: CER ≤15% → 채택 / 15~25% → 조건부 채택(정밀 자막싱크 등에는 안 쓰고 반복탐지·설명밀도 등 텍스트 근사만 필요한 용도로 제한) / >25% → 제외. Timestamp MAE ≤0.5초 → 채택 / 0.5~1.5초 → 조건부 / >1.5초 → 제외.

### 3-2. Burned-in 한국어 자막 탐지/OCR 정확도 — 일반 자막 vs 예능 자막 분리

**중요 (방법론 수정)**: Claude(저)가 프레임 이미지를 직접 보고 읽는 방식은 **OCR 정확도 측정으로 인정하지 않습니다.** 이 클라우드 작업환경은 외부 모델 가중치를 받을 수 없어 PaddleOCR/EasyOCR 같은 실제 OCR 엔진을 이 세션 안에서 돌릴 수 없으므로, 실제 OCR 엔진 실행은 사용자가 별도 PoC 환경(본인 PC 등, 인터넷 제한 없음)에서 진행합니다. 세부 실행 방법은 `poc/step4-0/OCR-EXTERNAL-EXECUTION-PLAN.md` 참고. 이 세션에서는 (a) 프레임 추출/사전필터 스크립트 제공, (b) 사용자가 별도 환경에서 실제 OCR을 돌려 만든 예측 결과 CSV를 받아 채점하는 역할만 합니다.

- **샘플 분리**: 테스트 샘플을 "일반 자막"(하단 고정, 단순 폰트)과 "예능 스타일"(색상/애니메이션/화면 각지 배치)로 미리 태깅해 별도로 채점한다.
- **Ground truth 제작**: 사람이 (a) 자막이 화면에 표시된 구간의 시작-종료 타임스탬프, (b) 그 구간 동안 실제 표시된 자막 텍스트 전문을 기록한다.
- **지표**:
  - 구간 탐지: interval-level Precision/Recall/F1 (예측 구간 시작/종료가 정답과 ±0.5초 이내면 매치로 인정)
  - 텍스트 정확도: 올바르게 탐지된 구간에 한해 OCR 텍스트 vs 정답 텍스트 CER
- **판정 기준(가설)**: 일반 자막 — 구간 F1 ≥0.85, 텍스트 CER ≤10% → 채택. 예능 자막 — 구간 F1 ≥0.7, 텍스트 CER ≤25% → 조건부 채택(예능 스타일은 "자막 존재 여부"만 쓰고 텍스트 정확도가 필요한 기능에는 미사용 등으로 제한). 기준 미달 시 제외.
- **자막-음성 싱크**: 별도 라벨링 없이 위 자막 구간 결과 + 3-1의 발화 구간 결과를 정렬해 계산(발화 구간과 자막 구간의 겹침 비율, 평균 시차).

### 3-3. 실제 editorial cut vs scene-change 검출 비교 — 장르별 분리

- **Ground truth 제작**: 사람이 영상을 보며 실제 편집 컷(장면 전환/컷 편집) 지점을 전부 타임스탬프로 마킹한다.
- **지표**: Precision/Recall/F1 (tolerance ±0.3초를 매치로 인정), **게임/스토리·썰/정보형 각각 별도 산출**.
- **판정 기준(가설, 장르별 독립 판정)**: F1 ≥0.8 → "컷 수"라는 표현으로 채택. 0.5~0.8 → "시각적 변화 빈도"로 표현을 낮춰 조건부 채택. <0.5 → 해당 장르는 이 항목 자체를 제외.
- 게임 장르는 연구 단계에서 이미 오탐 가능성이 높다고 확인되었으므로, F1이 낮게 나오는 것 자체는 예상된 결과이며 "그래서 컷 수 주장을 빼고 조건부로 간다"는 판단의 근거 자료로 쓴다.

### 3-4. Low-motion/static segment 검출 정확도

- **Ground truth 제작**: 최소 2명이 각자 "화면상 시각적 변화가 적다고 느껴지는 구간"(콘텐츠가 지루한지와는 별개 — 2026-08-23 정정, 0-1절 참고)을 독립적으로 표시한 뒤, 두 라벨이 겹치는 구간만 정답으로 채택한다(주관적 판단이므로 합의 구간만 인정해 노이즈를 줄임).
- **지표**: interval-level Precision/Recall/F1 (tolerance ±1초)
- **판정 기준(가설)**: F1 ≥0.7 → 채택. 0.5~0.7 → 조건부(임계값 재조정 필요 상태로 채택). <0.5 → 제외.

### 3-5. 영상 길이별 처리 시간

- 5분/10분/20분/30분 영상 각 1개 이상(가능하면 장르별로도 확보)에 대해 전체 파이프라인을 단계별(FFmpeg 단일 패스 / STT 호출 / OCR 호출)로 나눠 실측 소요 시간을 기록한다.
- 이 항목은 pass/fail보다는 **STEP 4-3 인프라 설계의 입력값**(예: Job 최대 실행 시간 설정, launcher timeout 설정)으로 사용한다.

### 3-6. 영상 길이별 예상 원가

- 3-5와 같은 샘플 기준으로, 실제 호출한 API(STT/OCR)의 공식 단가를 적용해 영상 길이별 원가 표를 만든다.
- 이전에 합의한 원칙대로, 여기서 나온 수치는 "이 PoC 실행 시점 기준" 값이며 실제 STEP 4-1 이후 구현 직전에 다시 한번 공식 최신 가격으로 재확인한다.

## 4. 기술별 채택 기준 종합

| 기술 요소 | 채택 | 조건부 채택 | 제외 |
|---|---|---|---|
| 한국어 STT | CER≤15% & TS MAE≤0.5s | CER 15~25% 또는 TS MAE 0.5~1.5s (용도 제한) | CER>25% 또는 TS MAE>1.5s |
| 자막(일반) 탐지/OCR | 구간F1≥0.85 & CER≤10% | 구간F1 0.7~0.85 또는 CER 10~25% | 구간F1<0.7 |
| 자막(예능) 탐지/OCR | 구간F1≥0.85 & CER≤10% | 구간F1 0.7~0.85 또는 CER 10~25% (존재 여부만 사용) | 구간F1<0.7 |
| Scene-change(장르별) | F1≥0.8 (컷 수로 표현) | F1 0.5~0.8 (변화 빈도로만 표현) | F1<0.5 (해당 장르 제외) |
| Static/low-motion | F1≥0.7 | F1 0.5~0.7 | F1<0.5 |

이 표의 판정 결과가 STEP 4-0 완료 시 `plan-v1-revised.md`의 항목별 구현 범위(신뢰도 높음/테스트 필요/생각보다 어려움 분류)를 다시 업데이트하는 근거가 됩니다.

## 5. 테스트 데이터 구성

**중요한 제약**: 이전 리서치에서 확정한 대로, 제3자(다른 크리에이터)의 YouTube 영상을 다운로드해 테스트 데이터로 쓰는 것은 YouTube API Services 정책의 다운로드/캐시 금지 조항과 충돌합니다. 따라서 테스트 샘플은 다음 중에서만 구성합니다.
- 사용자 본인이 직접 촬영/편집해 소유권이 있는 영상
- 이 프로젝트를 위해 새로 제작한 짧은 데모 영상(직접 게임 플레이 녹화 + 편집, 직접 스토리텔링 녹화, 직접 정보 전달 영상 등)
- 라이선스가 명확한 CC0/자유이용 소스

**샘플 구성(수정됨 — 1차 축소 시작 후 확대)**:
- **1차**: 게임 1개 / 스토리·썰 1개 / 정보형 1개 (각 3~5분) + 처리시간/비용 확인용 20~30분 영상 1개. 1차 결과가 의미 있게 나오면(도구가 정상 동작하고 최소한의 신호가 잡히면) 장르당 3개까지 확대한다.
- 각 3~5분 샘플에는 다음 분석 포인트가 **의도적으로 모두 포함**되도록 촬영한다(구체적인 초 단위 타임라인은 `poc/step4-0/test-video-shooting-scripts.md` 참고): 실제 편집 컷, 컷이 아닌 플래시/급격한 화면 변화(오탐 테스트용), 일반 자막, 컬러 자막, 테두리/그림자 자막, 큰 강조 자막, 화면 중앙/상단 자막, 짧게 등장하는 예능식 자막, 자막 없는 발화, 화면 변화가 적은 구간, 실제 freeze, 음량이 갑자기 커지는 구간, 음량이 지나치게 낮은 구간, 블랙프레임.
- 장르당 3개로 확대할 때도 한 영상에만 과적합되지 않도록 서로 다른 촬영/편집 스타일을 유지한다.

**라벨링 작업량에 대한 참고**: 자막 구간 + 컷 지점 + 정적 구간 + 발화 샘플 전사를 한 영상에 대해 모두 라벨링하면, 경험적으로 영상 실제 재생시간의 3~5배 정도 사람 작업 시간이 들 수 있습니다(실측 전 추정치이며 첫 1~2개 영상을 라벨링해보면서 보정 필요). 별도 라벨링 도구를 새로 만들지는 않고, 스프레드시트(타임스탬프/유형/텍스트 컬럼)나 무료 자막 편집기(예: Aegisub으로 자막 트랙을 만들어 타임스탬프를 뽑아내는 방식)로 충분합니다.

## 6. 실제 실행 순서

1. 테스트 영상 확보 (본인 소유/자체 제작, 장르별 3~5개, 길이 분산) — 코드 작업 없음
2. 사람이 직접 ground truth 라벨링 (스프레드시트/자막 파일) — 코드 작업 없음
3. 임시 스크립트로 각 기술 실행(FFmpeg 필터, STT API, OCR API 직접 호출) → 예측 결과를 json/csv로 저장
4. 채점 스크립트로 예측 vs 정답 비교, 3장의 지표 산출
5. 4장의 채택 기준표에 따라 항목별 판정, 결과를 `docs/step-4-0-results.md`(가칭)로 정리
6. 판정 결과를 바탕으로 `plan-v1-revised.md`의 V1 범위(항목 tier, 장르별 표현 방식)를 업데이트

## 8. 필요한 임시 스크립트/도구, production 코드 미접촉 원칙

- 모든 PoC 스크립트는 프로젝트 루트가 아닌 별도 스크래치 디렉터리(예: `poc/step4-0/`)에 작성한다.
- Next.js 앱의 `app/`, `lib/`, `components/`, `package.json`, DB 마이그레이션 파일은 이 STEP에서 전혀 건드리지 않는다.
- 임시로 필요한 라이브러리(예: Python STT/OCR SDK)는 격리된 가상환경(venv) 또는 1회성 실행(`npx`)으로만 사용하고 프로젝트의 의존성 트리에 추가하지 않는다.
- 모든 산출물(예측 결과, 채점 결과, 최종 리포트)은 로컬 파일로만 저장하며, production DB에 쓰지 않는다.
- 테스트 영상 원본 파일도 이 스크래치 디렉터리 안에만 두고 production Storage 버킷에 올리지 않는다.
