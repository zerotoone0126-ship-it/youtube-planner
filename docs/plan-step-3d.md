## 제안 1 (권장) — `submitOnboarding()`에 최소한의 예외 안전망 추가

### 문제
현재는 Supabase가 `{ data, error }` 형태로 "정상적으로 실패를 알려주는" 경우만 처리합니다. 네트워크 장애 등으로 호출 자체가 예외(throw)를 던지면 잡히지 않고 그대로 전파됩니다.

### 제안하는 변경 — `lib/actions/onboarding.ts`

**핵심 설계 원칙 (중요)**: `redirect()`는 내부적으로 예외를 던져서 동작하는 함수입니다 (`lib/actions/auth.ts`의 기존 주석: "redirect는 내부적으로 에러를 던져 흐름을 중단시킵니다. 그래서 try/catch로 감싸면 안 됩니다"). 그래서 **`try` 블록 안에는 DB 읽기/쓰기만 넣고, `redirect("/dashboard")` 호출은 `try` 블록 바깥, 즉 마지막에 그대로 둡니다.** 이렇게 해야 성공 시의 정상적인 리다이렉트가 실수로 "실패"로 잡히는 사고를 원천 차단합니다.

의사코드(실제 diff는 승인 후 제공):

```
if (!userId) redirect("/login")              // try 밖 — 그대로 유지
if (!parsed.success) return { error }         // try 밖 — 그대로 유지

try {
  // 기존 채널 조회
  // insert 또는 update
  // (여기서 error가 있으면 지금처럼 return { error } — throw 아님, catch와 무관)
  // profiles 업데이트
  // (마찬가지로 실패 시 return { error })
} catch (err) {
  console.error("[onboarding] 예상치 못한 오류", err);
  return {
    error: {
      code: "unexpected_error",
      message: "일시적인 오류가 발생했습니다. 잠시 후 다시 시도해주세요.",
    },
  };
}

redirect("/dashboard");                       // try 밖 — 성공 시에만 도달
```

### 왜 이 정도가 적절하다고 보는가
- 새 파일·새 의존성 없음. 기존 함수 하나만 최소로 손봄.
- 화면(`onboarding-form.tsx`)은 변경 불필요 — 이미 `response?.error`를 받아 같은 alert 박스에 표시하는 구조라, 이 새로운 에러도 기존 UI로 자연스럽게 표시됩니다.
- 앱 전체 에러 바운더리(`error.tsx`) 같은 더 큰 인프라 작업은 하지 않음 — STEP 3-D의 "마무리 점검" 범위를 벗어난다고 판단.

### 위험도
낮음. `redirect()`를 try 블록 밖에 두는 설계라 기존에 검증된 성공 흐름을 건드리지 않습니다. 다만 실제로 이 catch 분기를 브라우저에서 인위적으로 재현하기는 어렵습니다(네트워크 장애를 일부러 만들어야 함) — 아래 H(테스트 계획)에서 현실적인 검증 범위를 제안합니다.

## 제안 2 (비권장, 참고용) — 파일 상단 주석의 STEP 번호 정리

`app/onboarding/page.tsx`, `components/onboarding/onboarding-form.tsx`의 헤더 주석이 "STEP 3-B", "STEP 3-C부터" 같은 과정형 표현을 아직 담고 있습니다. 기능과 무관한 순수 문서화 문제입니다.

**제안: 이번엔 건드리지 않는 것을 권장합니다.** 이유:
- 정상 동작이 이미 검증된 코드에 기능과 무관한 이유로 diff를 만들면, "혹시 뭔가 바뀌었나" 재확인 부담만 늘어남
- 원하시면 이 항목만 별도로 나중에 가볍게 반영해도 늦지 않음

승인 여부만 알려주시면 되고, 승인 안 하셔도 다른 항목에 영향 없습니다.

## 제안 3 (권장) — 최종 검증에 `lint`/`build` 추가

지금까지 `npx.cmd tsc --noEmit`만 실행했습니다. STEP 3 전체를 마무리하는 시점이므로, 아래 두 명령을 한 번씩 더 실행해 확인하는 것을 제안합니다. **코드 변경이 아니라 확인 절차 추가**이므로 승인이 필요한 항목이라기보다는 아래 H절 테스트 계획에 포함해 바로 안내하겠습니다.

## H. 테스트 계획

| # | 시나리오 | 방법 | 기대 결과 |
|---|---|---|---|
| 1 | 정상 흐름 회귀 테스트 | 이미 완료된 계정을 다시 미완료로 돌리고 처음부터 재시도 | 이전과 동일하게 정상 저장 + `/dashboard` 이동 (제안 1이 성공 경로를 건드리지 않았는지 최종 확인) |
